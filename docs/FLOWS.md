# Flows — cross-system navigation and data paths

This owner maps implemented actor → screen/action → API/service → state/data → next owner. [DOMAIN](DOMAIN.md) and [bounded contracts](README.md) own business rules, status/grain semantics and mode invariants; [ARCHITECTURE](ARCHITECTURE.md) owns transport/trust, [DESIGN](DESIGN.md) presentation, [ENGINEERING](ENGINEERING.md#delivery-workflow) intake/acceptance and [OPERATIONS](OPERATIONS.md) release/runtime authorization. Do not copy their rule tables here or create a flow file for each small bug.

**Evidence level:** CURRENT below means inspected source, not deployed or executed acceptance. Runtime build/capabilities, active mode, worker settings and persisted results are NEEDS_EVIDENCE until separately authorized verification. UNKNOWN means a connector or outcome was not established; it is not permission to invent it. Role labels describe primary business responsibility, not exclusive command grants: backend policies/guards remain final.

## Navigation and shared entry

### F1 — Session and server-mode navigation

- **Actor / trigger:** A user signs in, refreshes the session or enters a protected route; a newer mode-authority hint triggers snapshot refresh.
- **Entry / permission:** Login → protected shell → permitted route. Authenticated `GET /api/system-operation-mode` supplies server authority; [Program](../backend/src/IPCManagement.Api/Program.cs) registers role-based API policies independently of frontend permission/navigation metadata. Admin mode initialize/change commands are outside ordinary navigation and need their own authorization.
- **Happy path / state:** Accepted session and mode snapshot → MainLayout / ModeGuard / RoleGuard → mode-aware page. MRX uses permitted dashboard/weekly-menu/warehouse/reconciliation/admin surfaces; its Chef cooking surface is in reconciliation, not DEFAULT Chef dashboard. DEFAULT purchasing is not a MRX branch.
- **Failures:** Login/session failure, denied route/action, unavailable mode snapshot, pending authority refresh/relocation, or invalid capability/navigation configuration remain explicit states. Moving between modes clears relevant client residue; it does not migrate business records.
- **Data read / write:** Session/profile, mode/capability snapshot and route scope read; token lifecycle and client selections change. Navigation itself does not post stock or documents.
- **API / modules:** [authApi](../frontend/src/features/auth/authApi.ts), [SystemOperationProvider](../frontend/src/app/providers/SystemOperationProvider.tsx), [mode controller](../backend/src/IPCManagement.Api/Features/SystemOperation/Controllers/SystemOperationModeController.cs), [AppRouter](../frontend/src/routes/AppRouter.tsx), [route registry](../frontend/src/routes/routeRegistry.ts), [eligibility](../frontend/src/lib/systemOperationEligibility.ts).
- **Jobs / notifications:** Mode authority hints/refetch are not evidence of cross-user business realtime. No staff notification channel is established by this navigation slice.
- **Expected result / acceptance:** The correct permitted page mounts under server authority; independently verify API denial and no cross-mode record/query leakage. `/__kit/planning/*` requires DEV or the exact preview flag plus its guards; mounted preview is not production cutover or acceptance.

## DEFAULT

### F2 — Planning sources to daily demand and kitchen-plan handoff

- **Actor / trigger:** Coordination prepares customer/week/menu/servings, generates demand, then sends the selected date/shift plan to Kitchen.
- **Entry / permission:** `/weekly-menu` and its permitted planning surfaces. Generation, staleness and direct demand approval use `DemandGenerateAccess`; production-plan reads use `ProductionAccess`, selected-date/shift send uses `CoordinationAccess`. Direct approval inherits Coordination-family generation policy even though the stored status says `MANAGERAPPROVED`; do not infer Manager-only authorization from that label.
- **Happy path / state:** Ready source inputs → daily generation → ProductionPlan/lines and MaterialRequest/lines → eligible request `DRAFT → MANAGERAPPROVED` → selected plan send fact → Chef's read surface. Week orchestration calls daily generation; it is not proof of one atomic weekly transaction.
- **Failures:** Missing effective BOM, incomplete servings, invalid scope/date/shift, conversion diagnostics or changed sources; regeneration can be blocked by approved/non-draft requests, physical issues or downstream purchasing documents. Preserve the source owner's exact response rather than inventing a universal recovery action.
- **Data read / write:** Read menu, completed quantity-plan lines, effective scoped BOM and unit/stock facts; write exact request/plan contributors, generation audit and handoff fact. Historical allocation/suggested purchase is neither current stock nor purchasing entitlement. Analytical export does not prove physical handoff.
- **API / modules:** `/api/material-demand/generate`, request approval and production-plan daily/send actions: [MaterialDemandController](../backend/src/IPCManagement.Api/Features/Planning/Controllers/MaterialDemandController.cs), [MaterialDemandService](../backend/src/IPCManagement.Api/Features/Planning/Services/MaterialDemandService.cs), [ProductionPlansController](../backend/src/IPCManagement.Api/Features/Planning/Controllers/ProductionPlansController.cs), [WeeklyMenuPage](../frontend/src/features/projects/pages/WeeklyMenuPage.tsx). Detail: [weekly-menu contract](domain/weekly-menu.md).
- **Jobs / notifications:** Request/cache refresh is not a staff notification or physical transfer. An external notification for generation/send is UNKNOWN in this slice; do not add a required realtime arrow.
- **Expected result / acceptance:** Inspectable daily request/plan lines and persisted selected handoff. Verify source readiness → each selected generation → correct source IDs → send → reload; preserve report-versus-command grain. Existing [demand-generation tests](../backend/tests/IPCManagement.Api.Tests/WorkflowGenerationTests.DemandGeneration.cs) define bounded expectations, not an executed whole-week result.

### F3 — Shortage, supplier decision, approval and purchase order

- **Actor / trigger:** Purchasing opens the scoped day/week workbench; an assigned authorized approver handles its target/step, then Purchasing explicitly creates orders from an approved request.
- **Entry / permission:** `/purchasing` decision panel and `/approvals`. Workbench uses `PurchaseAccess`; from-demand/evidence/decision/submit additionally use `PurchaseGenerateAccess`. Authenticated approval entry is not sufficient: ApprovalWorkflowService checks target permission, assignment and actor separation. Order reads use `PurchaseOrderReadAccess`; creation uses `PurchaseAccess`.
- **Happy path / state:** Exact demand lines → draft purchase request → supplier evidence/line decision → submit `DRAFT → SENTTOSUPPLIER` → applicable approval → separate `POST /api/purchase-orders/from-request/{purchaseRequestId}` requiring source `APPROVED` → compatible supplier/delivery/warehouse/terms groups produce `ORDERED` orders with original request-line decision snapshots. Submit is not automatic PO creation.
- **Failures:** Missing/changed source lines or supplier decisions, no eligible purchasing lines, unapproved demand/request, stale decision, wrong approver/assignment, missing rejection reason or incompatible established-order snapshots. Replayed established orders are validated, not blindly duplicated. Supplemental purchasing keeps its separate validated source path.
- **Data read / write:** Read approved demand and current supplier evidence; write request/line decisions, approval records and PO/lines. These are commitments, not receipts or stock movements.
- **API / modules:** `/api/purchase-workflow/*`, `/api/approvals/*`, `/api/purchase-orders/*`: [PurchaseWorkflowController](../backend/src/IPCManagement.Api/Features/Purchasing/Controllers/PurchaseWorkflowController.cs), [submission service](../backend/src/IPCManagement.Api/Features/Purchasing/Services/PurchaseRequestSubmissionService.cs), [ApprovalWorkflowService](../backend/src/IPCManagement.Api/Features/Approvals/Services/ApprovalWorkflowService.cs), [PurchaseOrdersController](../backend/src/IPCManagement.Api/Features/Purchasing/Controllers/PurchaseOrdersController.cs), [PurchaseOrderService](../backend/src/IPCManagement.Api/Features/Purchasing/Services/PurchaseOrderService.cs), [PurchaseDecisionPanel](../frontend/src/features/purchasing/PurchaseDecisionPanel.tsx) and [purchasingApi](../frontend/src/api/purchasingApi.ts).
- **Jobs / notifications:** Supplier email/dispatch and approver notification delivery are UNKNOWN, not implied by `SENTTOSUPPLIER`, an inbox or an outbox receipt.
- **Expected result / acceptance:** Reload exact supplier/source decisions, target approval and resulting orders; repeated create must preserve validated existing commitments. Do not certify delivered goods/stock from approval or order creation. Real actor/mode/version and persisted rejection/replay evidence remain required.

### F4 — Delivery evidence to inspected, approved, posted receipt

- **Actor / trigger:** Coordination records a PO delivery; Warehouse inspects; Manager approves; a permitted different Admin posts.
- **Entry / permission:** Receiving surfaces use `/api/warehouse/purchase-orders/{purchaseOrderId}/receipts`. Receipt reads use `InventoryReceiptReadAccess`; draft/rework uses `CoordinationAccess`, quality `WarehousePurchaseReceive`, receipt approval target permission plus Manager role, post/void `AdminAccess`. Route visibility does not determine who may create a draft.
- **Happy path / state:** Exact PO-line delivery evidence → draft/inspection → quality accepted/partially accepted and `PENDING_APPROVAL` → `APPROVED` → explicit `POSTED`. Only posting adds accepted stock, ledger/movements/lots and PO received progress; approval state and operational progress are different dimensions.
- **Failures:** Wrong PO/warehouse/source line, incomplete quality coverage, invalid accepted/rejected balance, stale version, creator inspecting or creator/inspector/approver posting. Full quality rejection changes no stock; allowed pre-post rework returns to inspection. Posted correction is append-only, not reset/delete.
- **Data read / write:** Read PO lines and canonical warehouse; write delivery/quality/approval evidence, then posting-owned stock/movement/progress/lifecycle/audit/idempotency facts. Preserve exact line provenance.
- **API / modules:** [WarehousePurchaseReceiptsController](../backend/src/IPCManagement.Api/Features/Purchasing/Controllers/WarehousePurchaseReceiptsController.cs), [PurchaseReceivingService](../backend/src/IPCManagement.Api/Features/Purchasing/Services/PurchaseReceivingService.cs), [ReceiptLifecycleWorkflow](../backend/src/IPCManagement.Api/Features/Purchasing/Services/ReceiptLifecycleWorkflow.cs), [warehouseApi](../frontend/src/api/warehouseApi.ts), approval target above; [warehouse contract](domain/warehouse-contract.md).
- **Jobs / notifications:** Lifecycle outbox staging exists; its currently registered consumer validates payload only. Staff/broker delivery is not established; see shared asynchronous boundary below.
- **Expected result / acceptance:** Draft/quality/approval reload still has no posting stock effect; post/replay has exactly accepted quantities and correct PO progress. [WarehousePurchaseReceivingTests](../backend/tests/IPCManagement.Api.Tests/WarehousePurchaseReceivingTests.cs) protect these boundaries; no real receiving acceptance was executed here.

### F5 — Material request to physical issue and whole-issue kitchen receipt

- **Actor / trigger:** Warehouse issues an approved original request; Kitchen checks its lines and acknowledges the whole issue. These are nominal owners, not exclusive server role scopes.
- **Entry / permission:** DEFAULT `/warehouse` and `/chef-dashboard`; `/api/inventory-issues` and `/{id}/confirm-receipt`. Current `InventoryIssueAccess` covers inventory **or production** roles for controller create/confirm; reader warehouse scoping adds another boundary. Do not document Warehouse-only create/Chef-only confirm as an implemented grant.
- **Happy path / state:** Approved DEFAULT request + original lines/version + stock checks → issue transaction and physical stock removal → subsequent whole-issue confirmation stores `ReceivedAt/ReceivedBy`. Local line checks do not persist partial kitchen receipt; confirmation is not ServiceRun close.
- **Failures:** Neither/both source families, mixed or changed lines, unapproved/stale request, wrong operational warehouse, insufficient stock, ambiguous source or mode mismatch. Confirmation replay returns the established received fact; grouped ingredient IDs cannot replace source-line commands.
- **Data read / write:** Read exact MaterialRequest/lines and allowance; write issue/lines, stock movements, audit/lifecycle/replay, then kitchen acknowledgement. DEFAULT physical handoff is gross history; compensating returns do not rewrite or reopen the original allowance.
- **API / modules:** [InventoryIssuesController](../backend/src/IPCManagement.Api/Features/Inventory/Controllers/InventoryIssuesController.cs), [InventoryIssueService](../backend/src/IPCManagement.Api/Features/Inventory/Services/InventoryIssueService.cs), [warehouseApi](../frontend/src/api/warehouseApi.ts), [chefApi](../frontend/src/api/chefApi.ts), [InventoryIssueServiceTests](../backend/tests/IPCManagement.Api.Tests/InventoryIssueServiceTests.cs). Grain/rules remain in DOMAIN/warehouse owner.
- **Jobs / notifications:** Transactional lifecycle staging and API invalidation are evidenced; neither proves cross-user delivery or notification.
- **Expected result / acceptance:** Correct issue lineage and stock/movement result, followed by all-line control → one persisted acknowledgement → reload. Check actual server actor denial and replay independently; generation allocation is not this result.

### F6 — Kitchen compensation and scoped ServiceRun close-out

- **Actor / trigger:** Chef reports shortage/return/actual servings; Warehouse fulfills supplemental or receives return; Admin handles permitted allocation disposition; an actor satisfying both close policies completes the run.
- **Entry / permission:** `/chef-dashboard` and warehouse compensation queues. Supplemental create uses `InventoryIssueAccess`, warehouse fulfill/purchasing-route/reject `InventoryAccess`; return create `ProductionAccess`, receive `InventoryAccess`, allocation disposition `AdminAccess`. ServiceRun open/start/record/confirm uses `ProductionAccess`; waive/resolve/close requires **both** `ProductionAccess` and `CoordinationAccess`, not either policy or every Chef.
- **Happy path / state:** Sent plan + exact customer/date/shift/tier sources → unique run/readiness → eligible start → serving evidence and exclusive confirmation/waiver → all blockers resolved → frozen close snapshot. Supplemental starts a new source-preserving supply loop; only confirmed return restores stock; later closed-run corrections are append-only deltas.
- **Failures:** Unsent or ambiguous source, unresolved supply/unreceived issue/open supplemental, missing servings/variance reason, competing confirmation outcome or unauthorized/invalid compensation. Do not invent a universal bypass or waiver.
- **Data read / write:** Read sent plan, issue-line readiness and actual serving facts; write compensation documents/ledger, serving decisions, run transitions/close snapshot and correction deltas. Preserve source issue/unit identity and four distinct readiness tracks.
- **API / modules:** [SupplementalMaterialRequestsController](../backend/src/IPCManagement.Api/Features/Inventory/Controllers/SupplementalMaterialRequestsController.cs), [InventoryReturnsController](../backend/src/IPCManagement.Api/Features/Inventory/Controllers/InventoryReturnsController.cs), [ServiceRunsController](../backend/src/IPCManagement.Api/Features/Planning/Controllers/ServiceRunsController.cs), [ServiceRunService](../backend/src/IPCManagement.Api/Features/Planning/Services/ServiceRunService.cs), [ServiceRunLifecycleTests](../backend/tests/IPCManagement.Api.Tests/ServiceRunLifecycleTests.cs), chefApi/warehouseApi above.
- **Jobs / notifications:** No external notification channel is proved by this slice. Inspect the affected producer/consumer before claiming delivery; operational readiness is separate from asynchronous receipt.
- **Expected result / acceptance:** Reload compensation source IDs/stock effect, serving decisions and all readiness tracks; close freezes the scoped result, corrections retain history. Kitchen acknowledgement alone does not complete this flow.

## ADMIN & REPORTING FLOWS

### F8 — Quản trị danh mục nguyên liệu, món ăn và định mức BOM gốc

- **Actor / trigger:** Quản trị viên (Admin) hoặc Bếp trưởng thiết lập danh mục nguyên liệu, món ăn, quy cách đơn vị tính, hoặc cập nhật định mức BOM per serving cho món ăn.
- **Entry / permission:** `/admin-data?view=ingredients`, `/admin-data?view=dishes`. Quyền truy cập: `AdminAccess` / `CatalogReadAccess` / `CatalogWriteAccess`.
- **Happy path / state:** Admin tra cứu danh mục nguyên vật liệu với phân trang server `pageNumber/pageSize` → Xem chi tiết định mức BOM của món ăn → Cập nhật công thức chuẩn (BOM gốc) làm căn cứ tính toán cho Thực đơn tuần và Kế hoạch sản xuất. Mọi thay đổi BOM giữ nguyên tính bất biến của các tuần thực đơn đã chốt (`BR-GLOBAL-03`).
- **Failures:** Thiếu đơn vị tính chuẩn (UnitId), trùng mã nguyên liệu, hoặc cố gắng sửa BOM của thực đơn đã khóa sổ sẽ bị chặn tại Backend API validation.
- **Data read / write:** Đọc danh mục `Ingredients`, `Dishes`, `DishBoms`; ghi nhận cập nhật phiên bản định mức với dấu vết kiểm toán người tạo/sửa.
- **API / modules:** [IngredientsController](../backend/src/IPCManagement.Api/Features/Catalog/Controllers/IngredientsController.cs), [DishesController](../backend/src/IPCManagement.Api/Features/Catalog/Controllers/DishesController.cs), [AdminDataPage](../frontend/src/features/admin/AdminDataPage.tsx), [adminApi](../frontend/src/api/adminApi.ts).
- **Expected result / acceptance:** Dữ liệu danh mục nạp đúng trang với phân trang server (`PagedResponseDto<T>`), không chứa trường nhân tạo (`categoryName` ảo); định mức BOM chính xác theo đơn vị tính chuẩn.

### F9 — Cấu hình quy tắc phê duyệt vận hành đa cấp

- **Actor / trigger:** Quản trị viên (Admin) cấu hình ma trận phê duyệt chứng từ (ngưỡng giá trị, vai trò duyệt, cấp bậc phê duyệt).
- **Entry / permission:** `/settings/approval-rules`. Quyền: `AdminAccess`.
- **Happy path / state:** Admin rà soát các quy tắc duyệt hiện hành cho Đơn mua hàng (PO), Đề xuất vật tư (PR), Phiếu xuất kho → Cấu hình ngưỡng phê duyệt và phân công vai trò (Manager / Director). Quy tắc mới có hiệu lực cho các chứng từ khởi tạo sau thời điểm lưu.
- **Failures:** Cấu hình thiếu vai trò phê duyệt, ngưỡng giá trị âm, hoặc vi phạm nguyên tắc tách biệt nghĩa vụ (Separation of Duties - SoD: người tạo không được tự duyệt) sẽ bị từ chối.
- **Data read / write:** Đọc và ghi các bản ghi `ApprovalRule` và `ApprovalStepDefinition`.
- **API / modules:** [ApprovalRulesController](../backend/src/IPCManagement.Api/Features/Approvals/Controllers/ApprovalRulesController.cs), [ApprovalRulesPage](../frontend/src/features/admin/ApprovalRulesPage.tsx).
- **Expected result / acceptance:** Hiển thị danh sách quy tắc chuẩn xác từ Backend, không dùng prompt/alert trình duyệt; cập nhật có xác nhận qua modal trợ năng.

### F10 — Khai thác hệ thống báo cáo vận hành và chi phí

- **Actor / trigger:** Quản lý, Kế toán, Thu mua, Thủ kho mở trạm Báo cáo để phân tích số liệu vận hành theo chu kỳ ngày/tháng.
- **Entry / permission:** `/reports?view=demand`, `/reports?view=prices`, `/reports?view=stock`. Quyền: `ReportAccess` / `InventoryReadAccess` trong chế độ `DEFAULT`.
- **Happy path / state:** Chọn kỳ báo cáo (tháng `YYYY-MM`) và bộ lọc đối tượng (Khách hàng) → Hệ thống nạp báo cáo tổng hợp nhu cầu vật tư (`ingredient-demand/aggregate/page`), biến động giá mua vào (`receipt-price-variance/page`), hoặc tồn kho hiện thời (`current-stock/page`) theo phân trang server 25 dòng/trang → Xuất bản dữ liệu phân tích với định dạng số chuẩn `<Num>` và ngày giờ Việt Nam (`Asia/Ho_Chi_Minh`).
- **Failures:** Mất kết nối mạng hoặc kỳ báo cáo không có dữ liệu sẽ hiển thị `StateBoundary` với trạng thái trống (`emptyTitle`) hoặc lỗi kèm nút `[Thử lại]`.
- **Data read / write:** Đọc dữ liệu tổng hợp (analytical projections); không phát sinh đột biến ghi sổ kho hoặc cập nhật chứng từ.
- **API / modules:** [DemandReportsController](../backend/src/IPCManagement.Api/Features/Reports/Controllers/DemandReportsController.cs), [PriceVarianceReportsController](../backend/src/IPCManagement.Api/Features/Reports/Controllers/PriceVarianceReportsController.cs), [InventoryOperationsReportsController](../backend/src/IPCManagement.Api/Features/Reports/Controllers/InventoryOperationsReportsController.cs), [ReportsPage](../frontend/src/features/reports/ReportsPage.tsx), [reportsApi](../frontend/src/api/reportsApi.ts).
- **Expected result / acceptance:** Tải báo cáo phân trang mượt mà không CLS, thời gian hiển thị theo chuẩn tiếng Việt, không tự suy diễn báo cáo chi phí suất ăn khi Backend chưa cung cấp hợp đồng.
